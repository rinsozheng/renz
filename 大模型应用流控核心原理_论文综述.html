Part 1：大模型推理的基本架构与关键流程

大语言模型的推理分为两个截然不同的阶段，它们在计算特性和资源消耗上存在根本差异：

Phase 1 Prefill（预填充阶段）

  • 一次性处理用户输入的全部 prompt tokens
  • 计算密集（Compute-bound）：利用 Tensor Core 做大规模矩阵乘法
  • 生成所有输入 token 的 Key-Value Cache
  • 吞吐率与 prompt 长度近似线性相关
  • GPU 利用率可达 80-95%

Phase 2 Decode（解码阶段）

  • 逐个（或小块）生成输出 token
  • 访存密集（Memory-bound）：每次只算一个 token，大量时间花在从显存加载权重
  • 每步需要读取全部模型权重（数十 GB）
  • GPU 利用率通常仅 5-20%
  • 输出长度不确定，无法预知

核心矛盾：Prefill 和 Decode 的资源需求完全不同 —— 一个需要计算力，一个需要内存带宽。混合运行时会互相干扰。

推理流程中的资源变化

理解资源消耗模式是设计流控系统的前提：

阶段计算类型GPU 利用率显存消耗持续时间
Prefill计算密集80-95%模型权重 + KV Cache 增长短（ms 级）但波动大
Decode Step 1访存密集5-15%模型权重 + 全部 KV Cache每步稳定
Decode Step N访存密集5-15%模型权重 + KV Cache 持续增长累积时间长

关键公式

Prefill 计算量 ∝ L² × D × H （L=prompt 长度，D=hidden dim，H=heads）
KV Cache 大小 ∝ 2 × L × num_layers × num_heads × head_dim × batch_size
Decode 每步延迟 ∝ Model_Size / Memory_Bandwidth

流控难点：Prefill 的计算量随输入长度 L² 增长，而 Decode 的显存占用随输出长度线性增长。两者都是不确定量，导致难以精确预测请求的资源消耗。

Part 2：核心问题 —— 输入 Token 算力的不确定性

流控面临的第一大挑战：无法预知一个请求需要多少算力

不确定性来源 1：Prompt 长度可变

  • 用户输入从几个 token 到数十万 token（RAG/长文档）
  • Prefill 时间与 prompt 长度呈 平方关系（attention 矩阵）
  • 短 prompt：几毫秒；长 prompt：数秒
  • 混合场景下，单个长请求可阻塞大量短请求

不确定性来源 2：输出长度不可预测

  • 无法提前知道模型会生成多少 token
  • 有的请求回复 2 个 token（是/否），有的回复 2000+ token
  • 输出长度直接影响 KV Cache 显存占用
  • 长输出请求会持续占用 Decode 槽位

不确定性来源 3：多请求并发干扰

  • 不同请求的 Prefill 和 Decode 阶段重叠
  • Prefill 会抢占 Compute Unit，拖慢 Decode
  • Decode 占满显存，新的 Prefill 无法进入
  • 导致 TTFT（首 token 时间）剧烈抖动

对传统流控的冲击

  • 传统 API 流控：简单 QPS / RPM 限制
  • 问题：每个请求的"重量"不同，等价的 QPS 不代表等价的负载
  • 100 个短请求 vs 1 个超长请求，对系统的影响完全不同
  • 需要 Token-aware 而非 Request-aware 的流控

算力不确定性的量化分析

用具体数字理解问题规模：

场景 A：短对话

Prompt: 50 tokens

输出: 30 tokens

Prefill 时间: ~2ms

KV Cache: ~0.5MB

总耗时: ~50ms

场景 B：文档问答

Prompt: 50K tokens

输出: 500 tokens

Prefill 时间: ~800ms

KV Cache: ~500MB

总耗时: ~2s

场景 C：长文生成

Prompt: 5K tokens

输出: 8K tokens

Prefill 时间: ~80ms

KV Cache: ~80MB

总耗时: ~15s

关键洞察：三个场景的资源消耗相差 100-300 倍！如果用传统 QPS 限流（比如限制每秒 10 个请求），在场景 A 下系统很空闲，在场景 C 下系统直接 OOM。

解决方案方向

方向 1：Token 预算制

限制并发 token 总数而非请求数，如"最多同时处理 100K input tokens"

方向 2：显存预算制

限制并发 KV Cache 占用，如"最多同时占用 60GB 显存给 KV Cache"

Part 3：关键瓶颈 —— 显存（VRAM）约束

大模型推理中，显存通常是第一瓶颈，而非计算力。

显存消耗组成

组件大小（70B 模型为例）特性
模型权重~140 GB (FP16)固定，加载一次
KV Cache动态，可达 20-60 GB随 batch 和序列长度增长
激活值较小（Prefill 阶段）Prefill 时瞬时较大
中间缓冲较小可复用

为什么是瓶颈？

  • A100 80GB：模型权重占 140GB → 必须多卡或量化
  • 即使模型放下，KV Cache 成为 动态瓶颈
  • KV Cache 增长不可预测 → 可能突然 OOM
  • GPU 显存无法像 CPU 内存那样轻松扩展
  • HBM 带宽有限（~2TB/s），Decode 阶段是主要限速因素

流控视角的显存约束：流控系统本质上是在管理一个有限资源池（显存），需要在"接受多少请求"和"每个请求占多少资源"之间做决策。

显存约束的公式化表达

流控系统需要实时跟踪以下约束：

VRAM_total ≥ VRAM_weights + VRAM_kv_cache + VRAM_activations + VRAM_buffer
VRAM_kv_cache = 2 × batch_size × avg_seq_len × num_layers × num_heads × head_dim × elem_size

关键决策变量

batch_size

可同时处理的请求数。增大提高吞吐但增加显存压力。

avg_seq_len

平均序列长度（含 prompt + 已生成 token）。不可控但可预估。

可调度空间

剩余显存 = VRAM_total - 已用。决定还能接纳多少请求。

流控核心问题：给定剩余显存 M_remain，应该接受多少个、什么样的新请求，使得（1）不会 OOM，（2）SLA 达标（TTFT 和 TPOT），（3）系统吞吐最大化？

流控的三维约束模型

综合以上分析，大模型流控需要在三个维度上同时做决策：

维度 1：显存容量

KV Cache 占用是硬约束。超出即 OOM。

控制手段：Token 预算、KV Cache 上限、请求驱逐

维度 2：计算力分配

Prefill 与 Decode 竞争 GPU Compute Unit。

控制手段：Prefill-Decode 解耦、时间片轮转、优先级调度

维度 3：SLA 保障

TTFT（首 token 时间）和 TPOT（每 token 输出时间）是核心指标。

控制手段：准入控制、速率限制、请求排队

请求到达
→
估算资源需求
→
准入决策
→
排队 / 接受 / 拒绝
→
调度执行
→
资源回收

Part 4：KV Cache —— 流控的核心对象

KV Cache 是流控系统中最重要的资源管理对象，理解它是理解所有流控技术的前提。

什么是 KV Cache？

在自回归生成过程中，每个 token 的 Key 和 Value 向量被缓存以避免重复计算。随着生成长度增加，KV Cache 持续增长。

KV Cache 的大小计算

per_token = 2 × num_layers × num_heads × head_dim × bytes

以 Llama-2-70B 为例：

  • 80 层 × 64 heads × 128 dim × 2 bytes (FP16)
  • per_token ≈ 1.6 MB / sequence
  • 100 个序列 × 1000 tokens = ~160 MB

KV Cache 的问题

  • 碎片化：不同序列长度不同，导致显存碎片
  • 不可预知：无法提前知道需要多少 cache 空间
  • 持续增长：decode 过程中不断分配新空间
  • 驱逐代价高：丢弃 KV Cache 意味着重新计算

KV Cache 管理技术谱系

围绕 KV Cache 管理，学术界提出了一系列创新方案：

与流控的关系：这些技术扩大了有效可用显存，直接改变了流控系统的"预算天花板"。但每种的副作用不同（量化有精度损失、驱逐有质量损失、offloading 有延迟惩罚），流控系统需要在决策时考虑这些 trade-off。

KV Cache 管理与流控的耦合

KV Cache 技术不是孤立的，它们深刻影响了流控系统的设计：

PagedAttention → 细粒度流控

将 KV Cache 分页后，流控系统可以以 page 为单位做精确的显存预算，不再需要预留大块连续空间。

流控影响：可以做更精确的 token 级别准入控制

Prefix Caching → 请求去重

相同前缀的请求可以复用 KV Cache，减少实际显存占用。

流控影响：流控系统应优先调度有 cache 复用的请求

KV 驱逐 → 弹性降级

当显存不足时，可以选择性地驱逐部分 KV Cache 而非拒绝整个请求。

流控影响：从二元决策（接受/拒绝）变为连续决策（接受但降级）

Offloading → 显存分层

GPU 显存不够时，将不活跃的 KV Cache 搬到 CPU 内存。

流控影响：流控预算可以从单一维度扩展到 GPU+CPU 两级

Part 5：连续批处理（Continuous Batching）

Continuous Batching 是现代 LLM serving 系统的基础技术，也是流控的前提。

传统静态批处理的问题

  • 必须等待 batch 中所有请求都完成 decode
  • 短请求被长请求拖慢（straggler problem）
  • GPU 在等待期间空闲
  • TTFT 高，用户体验差

Continuous Batching 的核心创新

  • 请求完成 decode 后立即退出 batch
  • 空出的 slot 立即被新请求填充
  • 无需等待整个 batch 完成
  • 显著提升吞吐（2-4x）和降低 TTFT

对流控的意义：Continuous Batching 使得"请求级别"的流控成为可能。因为请求可以独立进入和退出，流控系统可以实时决定什么时候插入新请求、什么时候暂停插入。

关键论文

Orca (2023) — 首次提出 iteration-level scheduling 与 continuous batching
vLLM (2023) — PagedAttention + continuous batching 的开源实现
TGI (Text Generation Inference) — HuggingFace 的 continuous batching 实现

Continuous Batching 的局限性

尽管 continuous batching 是基础，但它本身不能解决所有流控问题：

问题 1：Prefill 阻塞

新请求的 Prefill 仍然需要插入 batch，如果当前 batch 已满（KV Cache 占满显存），新请求只能排队等待。

问题 2：Head-of-Line Blocking

队列前面的长 prompt 请求阻塞后面的短请求，即使系统有足够的计算资源处理短请求。

问题 3：无优先级区分

标准的 continuous batching 对所有请求一视同仁，没有 SLA 感知或优先级调度。

问题 4：显存浪费

为每个请求预留最大可能 KV Cache 空间导致浪费。实际使用率通常只有预留的 30-60%。

这引出了后续一系列优化技术：Chunked Prefill、Prefill-Decode 解耦、智能调度策略等。

Part 6：Chunked Prefill —— 打破 Prefill 独占

Chunked Prefill 将长 prompt 拆分为小块，与 decode 交替执行，解决 Prefill 阻塞问题。

传统方式 vs Chunked Prefill：

传统： [Prefill(800ms)] → [Decode] → [Decode] → ...

Chunked： [Chunk₁(100ms)] → [Decode] → [Chunk₂(100ms)] → [Decode] → [Chunk₃(100ms)] → ...

优势

  • 消除长 Prefill 对 Decode 的长时间阻塞
  • 改善 TTFT 的 tail latency（P99）
  • 提高 GPU 利用率（Prefill 和 Decode 交替填充计算间隙）
  • 更好的 SLO 保障

关键论文

Sarathi-Serve (2024) — 提出 chunked prefill + 曲线感知调度
DistServe (2024) — chunked prefill 在解耦架构中的应用
vLLM chunked prefill — 开源实现中的 chunked prefill 特性
Llumnix (2024) — 全局调度中的 chunked prefill 集成

流控意义：Chunked Prefill 使得流控系统可以更细粒度地控制 Prefill 的资源占用，不再需要"全有或全无"的决策。

Chunk Size 的选择：关键权衡

Chunk Size 是 Chunked Prefill 的核心超参数：

Chunk SizePrefill 延迟Decode 干扰吞吐影响适用场景
小（64-128）低Decode 几乎不受影响Prefill 总时间增加（overhead）低延迟优先
中（256-512）中Decode 轻微影响较好的平衡通用场景
大（1024+）高接近传统 PrefillPrefill 吞吐高高吞吐优先

自适应 Chunk Size：最新的论文提出根据当前系统负载动态调整 chunk size —— 高负载时减小 chunk 保护 Decode，低负载时增大 chunk 加速 Prefill。

Part 7：Prefill-Decode 解耦架构

最激进的流控方案：将 Prefill 和 Decode 放到不同的 GPU 实例上运行，从根本上消除两者之间的资源竞争。

Prefill 集群
计算优化型 GPU
→ KV Cache Transfer →
Decode 集群
内存带宽优化型 GPU

核心优势

  • Prefill 和 Decode 完全隔离，互不干扰
  • Prefill 集群可以用大 batch 最大化吞吐
  • Decode 集群可以专注优化内存带宽
  • 可以独立扩展两个集群的规模
  • TTFT 和 TPOT 可以分别优化

挑战

  • KV Cache 传输开销：需要在 GPU 间传输大量数据
  • 调度复杂度：需要跨集群协调请求路由
  • 负载均衡：两个集群的比例需要仔细调优
  • RDMA / NVLink 等高速网络依赖

代表论文

DistServe (2024) — 首次系统性地提出 P/D disaggregation 架构
Mooncake (2024) — 基于 KVCache 传输的高效解耦 serving
Splitwise (2024) — 异构 GPU 上的 P/D 分离部署
APIServe (2024) — API 级别的解耦 serving 框架

解耦架构对流控的改进

Prefill 侧的流控

  • 可以独立设置 Prefill 的 token 预算
  • 专注于最大化 Prefill 吞吐
  • 可以安全地使用大 batch size
  • 无需担心影响 Decode 延迟

Decode 侧的流控

  • Decode 的 KV Cache 预算独立管理
  • 专注于最小化 TPOT
  • 接收的请求已经完成 Prefill，显存需求已知
  • 可预测性大幅提升

核心洞察：解耦架构将"不确定性问题"限制在了 Prefill 侧。Decode 侧接收的是已经完成 Prefill 的请求，其 KV Cache 大小已知，流控变成了确定性优化问题。

KV Cache 传输优化

技术方法传输延迟
RDMA零拷贝直接内存访问最低
P2P GPU 传输NVLink / PCIe P2P低
KV Cache 压缩量化后传输中
Prefetching提前传输预测的 KV Cache可变

Part 9：准入控制（Admission Control）机制

准入控制是流控系统的第一道防线 —— 决定哪些请求可以进入系统。

传统方法

  • 固定并发数限制：最多同时处理 N 个请求
  • 队列长度限制：排队超过 M 个请求时拒绝新请求
  • 简单令牌桶：固定速率放行请求

问题：不考虑请求的"重量"差异

LLM-aware 方法

  • Token 预算：限制总并发 token 数
  • 显存预算：限制 KV Cache 总占用
  • 预估拒绝：基于 prompt 长度预估资源，超出预算则拒绝
  • SLA 预估：预测新请求是否会导致已有请求 SLA 违约

优势：考虑了请求的异质性

关键决策逻辑

Accept if: (M_remain ≥ KV_est × cost_factor) AND (TTFT_est ≤ SLA_TTFT) AND (TPOT_impact ≤ threshold)

关键洞察：好的准入控制不只看当前资源是否够，还要预测加入新请求后对已有请求的影响。这需要建立准确的性能预测模型。

Part 10：速率限制（Rate Limiting）策略

速率限制是保护系统免受过载的最后一道防线。

令牌桶（Token Bucket）

固定速率补充令牌，每个请求消耗一个令牌。

不足：不考虑请求重量差异

漏桶（Leaky Bucket）

固定速率处理请求队列，平滑突发流量。

不足：延迟不稳定

Token-Aware 限流

每个请求按 prompt 长度消耗不同"令牌"。

优势：更精确反映实际负载

动态速率限制

根据系统当前负载自动调整限流阈值：

  • 显存使用率 < 70%：全速
  • 显存 70-85%：降低 50%
  • 显存 > 85%：仅接受高优先级

分层速率限制

不同层级设置不同的限流规则：

  • 用户级：每用户 RPM 限制
  • API 级：每端点 token/s 限制
  • 系统级：全局 KV cache 上限

Part 12：推测解码（Speculative Decoding）对流控的影响

推测解码通过用小模型预测多个 token 然后大模型验证，加速了 decode 阶段，但引入了新的流控变量。

推测解码的基本流程

  • 小模型（draft model）快速生成 N 个候选 token
  • 大模型（target model）一次性验证这 N 个 token
  • 接受的 token 直接输出，拒绝的重新生成
  • 平均接受率 60-80%，加速比 1.5-3x

对流控的新挑战

  • 每次 step 需要同时加载 两个模型的权重
  • 显存占用增加（draft model 的权重 + KV cache）
  • 验证失败的 token 需要回滚，KV Cache 管理更复杂
  • 接受率不确定，进一步增加了算力不确定性

推测解码下的流控公式

引入推测解码后，流控系统需要额外考虑以下变量：

VRAM_spec = VRAM_target + VRAM_draft + KV_cache_target + KV_cache_draft
Speedup ≈ 1 / (1 - α × accept_rate) where α = draft_speedup_factor

流控调整策略

  • 根据当前显存剩余决定是否启用推测解码
  • 动态调整 draft length（推测步数）
  • 显存紧张时降级为标准解码
  • 优先对高优先级请求启用推测解码

实际建议

  • 显存使用率 < 60%：开启推测解码，draft length=4
  • 显存 60-80%：开启推测解码，draft length=2
  • 显存 > 80%：关闭推测解码，节省显存
  • 始终监控接受率，低于 50% 时关闭

Part 13：多 GPU / 多节点扩展

单 GPU 无法满足生产需求时，流控系统需要跨多个 GPU 和节点协调。

扩展方式

  • Tensor Parallel (TP)：模型切分到多张 GPU，单请求跨多 GPU 执行
  • Pipeline Parallel (PP)：模型分层切分，请求在 GPU 间流水线执行
  • Data Parallel (DP)：每个 GPU 放完整模型副本，请求分配到不同 GPU
  • 混合并行：TP + DP 是最常见的生产配置

流控挑战

  • DP 需要请求路由/负载均衡决策
  • TP/PP 需要跨 GPU 同步 batch
  • 不同 GPU 的 KV Cache 状态需要全局跟踪
  • 负载不均衡会导致部分 GPU 空闲

多 GPU 负载均衡策略

在 Data Parallel 或多实例部署中，如何将请求分配到不同的 GPU 实例？

策略原理优点缺点
Round Robin轮流分配简单不考虑负载差异
Least Loaded分配给最空闲的实例负载均衡需要全局状态同步
Prefix-Aware优先分配到有 KV Cache 前缀的实例减少 Prefill 开销可能不均衡
SLO-Aware Routing分配到最可能满足 SLA 的实例SLA 合规率高预测模型复杂
Token-Budget Routing分配到 token 预算最充足的实例资源利用率高需要实时预算跟踪

趋势：现代多 GPU 系统趋向于 Prefix-Aware + Token-Budget 的混合路由策略，在保证负载均衡的同时最大化 KV Cache 复用。

大模型流控系统的设计建议

基于对 100+ 篇论文的综合分析，我们总结以下设计建议：

1. 以 Token 为流控单位

不要用 QPS/RPM 做流控，应该用 token 预算或 KV Cache 显存预算。每个请求的"重量"差异太大，简单的请求数限制无法反映真实负载。

2. Prefill 与 Decode 分离

至少在同一 GPU 上做时间片隔离（chunked prefill），最好在不同 GPU 上做物理隔离（P/D disaggregation）。

3. 使用分页 KV Cache

PagedAttention 类技术可以消除显存碎片，使得流控预算更加精确和高效。这是现代 LLM serving 的基础设施。

4. SLO 驱动的准入控制

准入决策不应只看当前资源是否够，还要预测加入新请求后对已有请求 SLA 的影响。建立准确的性能预测模型。

5. 动态调整，而非静态配置

chunk size、batch size、推测解码参数等都应根据系统当前负载动态调整。静态配置在不同负载下都无法最优。

6. 多层防护

流控应该有多个层次：Token 预算 → 准入控制 → 速率限制 → 请求排队 → 优雅降级。每一层都是安全网。

未来研究方向

短期（1-2 年）

  • 自适应流控：基于在线学习的自动参数调优，无需手动配置
  • MoE 流控：Mixture-of-Experts 模型的路由选择与资源分配耦合
  • 多模态流控：图像/视频输入带来的新维度的不确定性
  • 端云协同：端侧小模型 + 云端大模型的协同流控

中长期（2-5 年）

  • Agent 工作流流控：多步 Agent 调用链的资源编排
  • 跨组织联邦推理：多租户/多组织的联合资源调度
  • 新型硬件适配：CXL 内存、光计算等新硬件上的流控范式
  • 形式化验证：流控策略的 SLA 保障可证明性

总结：大模型流控的核心挑战源于两个根本不确定性 —— 输入 token 算力不确定性和输出长度不可预测性。解决这些问题的关键路径是：Token 级别的精细流控、Prefill-Decode 解耦、以及 SLO 驱动的自适应调度。
